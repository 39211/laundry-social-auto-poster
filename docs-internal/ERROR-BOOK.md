# 私享家產線踩坑簿(每個都真的發生過)

> 規則:每踩一個新坑,**當天**加一條。格式固定:`症狀 → 真因 → 修法 → 怎麼再驗一次`。
> 這份是給接手者看的。**動手前先掃一遍與你任務相關的段落**,不要用別人的血再流一次。

## A. 內容正確性(最貴的坑,會直接發錯東西給客人)

### A1|改了主題卻沒改圖片提示詞 → 文不配圖上線
- **症狀**:貼文寫「書包背帶」,圖是帆布鞋。
- **真因**:我改了 `topic` 和 captions,忘了 `image_prompt` 與 4 張輪播的 prompt 是獨立欄位。
- **修法**:改主題必須**同時**改 `image_prompt` + 每個 `carousel_items[].image_prompt`,刪舊圖、刪 day-lock、重生圖、**親眼看圖**、重鎖。
- **再驗**:生成後開圖看,不是看檔案存在。已加「文不配圖閘」(manifest fail-closed),但閘擋的是缺圖,**擋不了畫錯東西**——只有人眼能擋。

### A2|已存產出陷阱:改了生成器,行事曆還是舊內容
- **症狀**:改完 prompt 規則,產出完全沒變。
- **真因**:當日行事曆 JSON 已經存在,裡面帶著**上一版產生的成品文字**,生成器不會覆蓋已存欄位。
- **修法**:改生成器後,要嘛刪當日行事曆重生,要嘛直接改行事曆裡的欄位。踩過三次。
- **再驗**:改完後 grep 行事曆確認新規則的特徵字串真的出現。

### A3|舊 day-lock 把新內容打回去
- **症狀**:明明改成書包,隔天變回床組。
- **真因**:day-lock 是「當日內容正本」,heal 機制會拿鎖去覆蓋行事曆。鎖是舊主題,就把新的救回舊的。
- **修法**:**刻意重做流程** = 先刪 `data/day-locks/<date>.json` → 改內容 → 驗圖 → `npm run day-lock -- --date <date>` 重鎖。
- **再驗**:重鎖後比對 `day-locks/<date>.json` 的 topic 與行事曆 topic 一致。

### A6|閘門問的證人可以改口供:重跑 manifest 就把紅燈變綠燈
- **症狀**:8/14 slot 1 被文不配圖閘正確擋下(圖是帆布鞋、文案是白鞋)。我跑了 `generate-image-manifest` 想看新提示詞,**沒有重生任何一張圖**,閘門就變綠了。硬碟上還是帆布鞋。
- **真因**:閘門拿「行事曆的 topic」比對「image-prompts manifest 的 topic」,而 **manifest 是隨時可以重建的檔案**。一份寫在圖之後的文件,沒有資格替那張圖作證。
- **修法**:加第二個證人——`mark-image-source` 在**寫檔的當下**把 topic 蓋在每個檔案的來源紀錄上,閘門改比對它;沒蓋到就當作未證明(fail closed)。兩個證人都要過。
- **再驗**:三態突變實測(`test/imageTopicWitness.test.ts`)——主題不符→擋並指名檔案、沒有主題→擋、主題相符→不擋;把新迴圈拿掉,3 條裡 2 條變紅。
- **邊界(2026-08-14 三席複審後改寫,原本那段自己就寫錯了)**:
  原文說「擋的是自動化失效,擋不了人手動重跑」。**兩個方向都不準**——
  ①**高估**:同屬自動化的 A1 路徑照樣全綠(改主題與文案、忘了改 `image_prompt`、
  刪圖、`generate-missing-images.ps1` 依過期 prompt 重生並重蓋章)。
  蓋的是**當下行事曆的 topic**,不是圖片實際被什麼提示詞生出來的。
  ②**低估**:繞過面不只「手動重跑」,還有 `approve-post`(零圖文檢查直接寫核准)、
  核准後換圖(補跑鏈見到 approved-log 就不重審)、slot 2/3 完全不檢查。
- **仍未關的**:要真正成立,蓋章必須同時帶 **PNG sha256** 與 **prompt hash**,
  且只在位元變更時才准改;檢查要套到**每一格、每一張**。
- **通則**:🔴 **問閘門「你的證據是誰寫的、什麼時候寫的」。** 證據若能在被驗的東西之後被重寫,它證明的是那份文件,不是那個東西。
- **通則二**:🔴 **自己寫的「邊界宣告」也要被審。** 我以為誠實列出限制就夠了,
  結果那段宣告同時高估與低估——**它讀起來像克制,實際上是另一種沒查證的斷言**。

### A9|我的測試只測讀的那一半,寫的那一半刪掉還是全綠
- **症狀**:grok 設計的突變——把 `markImageSource` 裡 `topic: dailySlot.topic` 整行刪掉——**213 條測試全綠**。整個蓋章機制可以消失而沒有任何一條測試發現。
- **真因**:`test/imageTopicWitness.test.ts` 用 `writeSource()` **手寫 JSON** 餵給閘門,從頭到尾沒有呼叫過真正的 `markImageSource()`。我測的是「閘門讀得對不對」,不是「章有沒有被蓋上去」。
- **更糟的一條**:原本三則測試**從不寫 `data/image-prompts/<date>.json`**,所以第一證人永遠走 `catch`。也就是說**事故本身的形狀(manifest 已對齊、檔案還是舊的)沒有任何測試**。grok 設計的 3b 探針補上後,把第二證人搬進 `catch` 的突變才會變紅。
- **再驗**:三個突變的預測與實測**逐項相符**(2 紅 1 綠 / 3 綠 / 3a 綠 + 3b 紅)。
- **通則**:🔴 **一個機制有「寫」和「讀」兩側,測試要能分別殺死它們。** 只用手寫 fixture 餵讀側,寫側就是零覆蓋——而且看起來覆蓋率很好。問法是:**「把產生這份資料的那段程式刪掉,測試會紅嗎?」**

### A7|圖片在 06:30 生成、文案在 10:20 改掉,沒有人負責讓它們重新對上
- **症狀**:8/14 slot 1 圖文不一致,整個上午的補跑鏈(11:35/12:05/13:30/13:50)都沒發出去,當天只出了一則。
- **真因**:圖片是照 06:30 的 manifest 生的,主題之後變了,而**沒有任何一步會因為主題改變去重生圖片**。閘門正確擋下,但擋下之後沒有自動修復路徑,只能等人。
- **修法(當日)**:重生 manifest → 移走舊圖 → `scripts/generate-missing-images.ps1` → 重新核准 → `ALLOW_OFF_SCHEDULE_PUBLISH=true` 補發。
- **未修**:自動修復尚未存在。閘門會擋,但沒人會修——**這是目前最可能讓某一天只出半天內容的路徑**。
- **通則**:**擋下來不等於救回來。** 每個 fail-closed 閘門都要問「擋下之後,誰負責讓它變綠」;沒有答案就等於把停機時間交給運氣。

### A8|「已經有了就跳過」的判斷條件寫錯,規則就永遠不會套用
- **症狀**:8/14 中午發的 Reel 文案裡沒有可點的 LINE 連結、沒有價格、四個 hashtag 沒有一個是地區標。同一天的圖文貼文三樣都有。
- **真因**:兩層。①`scheduleReel.ts` 自己組文案,完全沒走 `contentPlan` 的共用規則(聯絡行/價格行/hashtag 階梯);②就算走了也沒用——`withLineContact` 的跳過條件是 `caption.includes("0968327653")`,而 Reel 文案裡寫的是「加 LINE 直接問:0968327653」,**號碼在、連結不在**,規則自己判斷「已經有了」就跳過。
- **後果**:GA4 的 `line_click` 是靠那個轉址連結記的。**每一支 Reel 都是不可量測的**——而 Reel 正是每天唯一穩定出的內容。花力氣把讀取端建起來,寫入端卻對一半的產出不生效。
- **修法**:①匯出 `withSharedCaptionRules(caption, topic)`,Reel 文案送進去;②跳過條件改判**轉址網址**而不是電話號碼。
- **再驗**:突變實測——把 Reel 那兩行改回不套用,`test/abTestPipeline.test.ts` 立刻變紅(缺地區標);測試同時斷言轉址網址必須在。
- **通則**:🔴 **「這個規則有沒有已經套用過?」的判斷,要認規則本身的產物,不要認一個近似特徵。** 電話號碼不是可點連結,而拿號碼當「有聯絡方式了」的證據,等於讓最弱的形式取消最強的形式。與 [A6] 同源:**證據要能證明你真正在意的那件事**。

### A10|閘門要求的證據,產線寫手交不出來 = 排定好的停機
- **症狀**:我把圖文舉證要求套到每一格之後,兩席複審同時指出:10:20 的 `daily-approve.ps1` **先跑 `heal-reel-slot` 再跑 auto-approve**,而 `scheduleReel` 寫的封面紀錄只有五個欄位(沒有 topic、沒有雜湊)。閘門會把它讀成「未證明」→ Reel 格被擋 → 當天只核准 slot 1 → 補跑鏈見到 approved-log 就不再重審 → **Reel 一整天發不出去**。
- **真因**:我加嚴了「要求」,卻沒同步升級**產線實際使用的那個寫手**。閘門與寫手是一組的,只動一邊就是把停機排進行事曆。
- **修法**:Reel 封面改走 `markImageSource`(帶 topic + 兩個雜湊),並自己補寫 manifest 條目(manifest 06:30 從行事曆生成,10:20 才 heal 進來的封面不在裡面)。
- **再驗**:還原成五欄寫法 → 測試變紅。
- **通則**:🔴 **加嚴閘門前,先列出「有哪些寫手會產生要被檢查的東西」,逐一確認它們交得出新證據。** 一個產線交不出證據的閘門,不是閘門,是停機。

### A11|只有一半的讀者認得的旗標,等於沒有旗標
- **症狀**:`data/ab-test-plan.json` 從 7→3 減量那天就寫了 `paused: true`,但**只有 PowerShell 產線讀它**;TypeScript 的 `planSlot` 照發不誤,所以 heal 會把已經退場的晚間 Reel 塞回當天。

- **再驗**:忽略 paused → 測試變紅。
- **通則**:**一個決定要在所有讀者眼中同時成立,才叫決定。** 加旗標時先數清楚有幾個讀者。

### F12|從未執行過的路徑,首次真實執行就是它的第一次測試
- **症狀**:8/16 是第一個治療 A 日,`Invoke-TreatedAssembly` 每次都 `produced no file`,看不到任何 ffmpeg 錯誤。這段程式 8/11 就寫好了,躺了五天。
- **真因(三層)**:①`"fontsize=$hookSize:fontcolor=white"` —— PS 雙引號字串裡變數後面直接接冒號,`$hookSize:fontcolor` 被解析成 scope 限定變數(同 `$env:PATH` 語法),不存在=展開為空,ffmpeg 收到 `fontsize==white` 直接炸,六處 drawtext 全中;②當天 suede 這對片實測增益 R 2.1047,超出 `colorchannelmixer` 的硬上限 [-2,2],filter 初始化整組失敗;③兩個錯都躲在 `2>&1 | Out-Null` 後面,外面只看得到「檔案沒生出來」。
- **修法**:六處改 `${hookSize}`/`${closeSize}`;增益解析處夾住 ≤2(寧可色彩略欠校正也不要沒有片);ffmpeg stderr 落地 `ffmpeg-treated.log`,throw 訊息帶最後 5 行。
- **再驗**:修完產線跑出 15s-tA+10s 控制組,兩支 `.subs.json` 都 `burned=true`;還原任一修法即重現原錯,錯誤訊息這次看得見。
- **通則**:🔴 **代碼寫好躺著 ≠ 能跑;「還沒執行過的分支」就是還沒測試過的分支。** 治療剪 8/12-14 三天都因機器睡著沒跑,大家以為它 ready,其實它從未活過。吞掉 stderr 的地方,「真 bug」與「檔案沒生出來」長得一模一樣 —— 診斷成本全轉嫁給下一個人。

### F11|把別人改到一半的檔案掃進自己的 commit,自己的測試綠救不了你
- **症狀**:8/16 整個上午發布 crash 在 import(缺三個匯出),slot 2/3 核准了發不出去,到 13:30 才有人發現。
- **真因**:並行 session 在改 postCurrentSlot+imageStamp+logging;我提交 d0c82e8 時把**它改到一半的 postCurrentSlot** 一起 staged(我的 typecheck 是在它後續修改落地**之前**跑的);它的 imageStamp/logging 還沒提交,06:30 的 stash 守衛照設計把那些暫存 → HEAD 的 import 指向不存在的定義。
- **陷阱疊加**:我先把鍋甩給自動 Pages commit(A-2 原判),查證後發現該 commit 是 pathspec 限定、stash 守衛也有效 —— **兩層保護都在,漏的是我自己的 staging 紀律**。
- **修法**:看到「檔案被並行修改」的提醒後要 commit 該檔,**必須在 `git add` 之後、`git commit` 之前重跑 typecheck**;或干脆不把該檔納入這次 commit。
- **通則**:🔴 **測試綠只證明「跑測試那一刻」的樹,不證明「你 commit 那一刻」的樹。** staging 與驗證之間每多一秒,並行寫入就多一秒的窗。

## B. 驗證方法本身出錯(最陰險:讓你以為壞了,或以為好了)

### B1|cp950 假陰性:中文比對「不報錯、直接 0 命中」
- **症狀**:驗證 YouTube 描述,回報「參考價/至善國中/儲值全都沒有」——實際上線上全都有。
- **真因**:內容經過 shell 管線/檔案落地時被 cp950 毀了,我拿**損壞的資料**去比對,Python 又用 `errors='replace'` 吞掉,毫無錯誤訊息。
- **修法**:中文比對**抓取與比對必須在同一個 Python 程序內完成**,不經過 shell 管線、不落地中間檔。
- **再驗**:同一份內容故意打錯一個字,比對必須變 False——比對器要能分辨真假,不然它只是在說「找不到」。

### B2|退出碼與自述不可信
- **症狀**:腳本 exit 0,但實際沒發文;或 exit 非 0,但其實發成功了。
- **真因**:發布鏈有多段,退出碼只反映最後一段。
- **修法**:發布真相**只看 `data/posted-log/<date>.json`**;YT 看 `data/youtube-log/`;結算看 `output/day-reports/`。
- **再驗**:任何「已完成」都要指出是哪個檔案的哪一筆記錄。

### B3|閘門自己壞掉時等於全放行(Grok 紅隊找到,最重的一條)
- **症狀**:PreToolUse 閘門拋例外 → exit 1;但攔截條件是 exit 2 → **全部放行**。
- **真因**:fail-open 預設。
- **修法**:閘門一律 fail-closed;例外路徑也要回攔截碼。
- **再驗**:故意讓閘門拋例外,確認它擋下來而不是放行。

### B4|檢查器搜的是「我在對話裡發明的名字」,不是程式裡真實存在的字
- **症狀**:驗證「船長方法有沒有真的進生產」,回報三幕相機節拍「文件無、生產無」——實際上它完整存在於 `scripts/produce-next-reel.ps1:508-519`。
- **真因**:我搜 `push-to-defect`／`hold-on-contact` 這類**簡稱**,那是我在對話裡為了溝通方便造的詞,程式裡寫的是完整英文指令(`a slow push-in that ends framed on the worn area`)。**簡稱只活在對話裡。**
- **修法**:查「某個概念有沒有被實作」時,先打開檔案看它**實際怎麼命名**,再用那個字串搜;或搜行為特徵(函式名、switch 分支)而不是概念名。
- **再驗**:對一個**已知存在**的功能跑同一套檢查,回 False 就是檢查器壞了,不是功能不見了。
- **與 B1 同源**:兩者都是「驗證方法本身出錯,而且錯得很有說服力」。

### A4|同一支影片配同一則文案,隔天再發一次(2026-08-07~11 發生四次)
- **症狀**:IG 上 8/10 12:01 與 8/11 20:31 是同一支皮鞋影片、同一則文案;窗簾、後背包同樣各兩次。觸及從 169 掉到 26-87。
- **真因**:`generateDailyContent.ts` 保留「已排定的 reel slot」時保留**整個 slot 物件**,文案跟著影片從前一天中午被帶到隔天晚上。程式碼註解只想保住影片檔,實際連文字一起保住了。
- **修法**:只保留媒體欄位(`media_type`/`local_video_path`/`topic`),文案永遠屬於當天;另加發布端查重閘(近 7 天有逐字相同且真的發布過就拒發)。
- **再驗**:突變實測——拿掉查重閘,`test/publishGuards.test.ts` 必須變紅(已驗證)。

### B5|dry-run 寫出空的指紋檔,反而讓指紋閘失效
- **症狀**:`data/approved-log/2026-08-12.fingerprints.json` 內容是 `{}`,而當天核准檔根本不存在。
- **真因**:dry-run 跳過核准紀錄卻仍寫指紋檔;而發布端寫 `if (expected && expected !== actual)`,**沒有條目就短路放行**。檔案存在 = 宣稱已指紋化,但實際不檢查任何東西。
- **修法**:指紋寫入移進 `if (!options.dryRun)`;發布端把「有指紋檔但缺這個 slot」改成**拒發**。
- **再驗**:突變實測——把缺項判斷改成永不成立,測試必須變紅(已驗證)。
- **通則**:**空的保護檔比沒有保護檔更危險**,因為它讓檢查看起來存在。

### B6|測試全綠不代表保護有效——刪掉保護仍然全綠
- **症狀**:199 個測試全綠,但跨家族審核把七天重複閘、文不配圖閘、指紋比對、單飛鎖、NonRetryableError、healDay 逐一刪掉重跑,**結果與基準完全相同**。
- **真因**:那些機制**根本沒有對應測試**(grep `fingerprint`/`dayLock`/`NonRetryableError` 於 test/ 零命中)。
- **修法**:寫測試時同時做突變實測——拿掉被保護的那一行,測試必須變紅;不會變紅的測試要刪掉,不要留著當防禦縱深。
- **實證**:我今晚新寫三條,其中一條(dry-run 不留痕)拿掉保護仍全綠,因為 autoApprove 在寫指紋前就先拋錯 → **已刪除該條**,不留假綠。

- **通則**:**實驗的觸發條件不可以跟生產的觸發條件共用**。得到「無效」時要先問「它到底有沒有被執行過」。

### F6|用絕對座標排版,元素會互相疊上去而且不會報錯
- **症狀**:海報 v4 第一版的 QR 白框直接壓在優惠塊文字上。
- **真因**:各元素用 `H - 固定值` 各自定位,沒有人負責檢查總高度。
- **修法**:改成由上到下累加的 mm 預算,存檔前 `assert` 總和與底部界線。
- **再驗**:故意把某段高度加大,assert 必須擋下來。

### F7|只算區塊高度、不算文字實際佔高,文字會壓在下一個元素上而不報錯
- **症狀**:海報 v5 第一版「儲值 1000 送 100」壓在「運動鞋 $250 起」上面。v4 也犯過同型(QR 壓優惠塊)。

- **修法**:畫字的函式回傳「文字底部座標」,後續元素一律以它為起點;每個容器存檔前斷言內文底部 ≤ 容器底部。
- **再驗**:故意把字級調大 20%,斷言必須擋下來(v5 實測擋下了兩次)。

### F8|用眼睛決定字級,就會做出走過去才看得到的海報
- **症狀**:v3/v4 的副標 7.5mm、優惠 10mm —— 分別要走到 0.9m 與 1.2m 才讀得到,而海報貼在門口是給 2-3m 外的人看的。
- **真因**:沒有把「這個字要在幾公尺外被讀到」變成參數,只憑畫面比例挑大小。
- **修法**:字高 = 閱讀距離(m) × 8.33(業界規則:1 英寸/10 英尺);先宣告每個元素的目標距離,字級由公式產生。主圖高度是可以退讓的,字高不行。
- **再驗**:拿同一把尺回頭量舊版,失敗項要能被指認出來(已量,v3/v4 各三項不合格)。

### E4|「發布後絕不重試」只在單一行程內成立,補跑鏈照樣重發
- **症狀**:8/11 slot 2 IG attempts=2;圍堵令記載 dual-Reel publication。
- **真因**:三層洞。①FB 發布端(photos published:true、Reel finish、輪播 /feed)完全沒有 commit 保護,普通 Error → withRetry 重跑整條上傳;②IG 的 response.json() 在 try 外,回應在傳輸中斷線 = 可重試的 SyntaxError —— 正是它要擋的那種情況;③commit 失敗記成 "failed",補跑鏈把 failed 讀成「沒發過」→ 兩小時後再發一次。
- **修法**:兩平台 commit point 統一白名單制(只有明確成功可繞過,其餘一律 NonRetryable);新增 posted-log 狀態 "uncertain",hasRecordedPost 視為已記錄,人工查後台後才清除。
- **再驗**:突變實測 —— 把 uncertain 從 hasRecordedPost 拿掉,測試變紅(已驗)。
- **通則**:**「絕不重試」要在每一個會重新進場的路徑上成立**:行程內(withRetry)、跨行程(補跑鏈)、跨日(排程救援)。只擋一層等於沒擋。

### D4|機器睡著 = 整天靜默不發,而所有檢查都看不到
- **症狀**:2026-08-12、08-13 連續兩天一則都沒發。程式沒有任何錯誤、測試全綠、排程全部 Ready。
- **真因**:所有排程 `WakeToRun=False`。機器睡著時 Task Scheduler **不會叫醒它**,而 `StartWhenAvailable=True` 讓它「醒來後再補跑」——8/13 23:40 開機時所有錯過的任務一次全跑,隨即又被關機殺掉(`LastTaskResult=3221225786` = 0xC000013A,行程被強制終止)。發布視窗那時早就過了。
- **為什麼沒被發現**:夜檢只檢查「明天備妥了沒」,從來不問「**今天到底發出去了嗎**」。所有指標都在講未來,沒有一個看當下。
- **修法**:①發布鏈五個排程設 `WakeToRun=True` + 允許電池供電時執行;②夜檢加第 10 項:posted-log 沒有任何 success/posted 就判 HIGH,並直接檢查 WakeToRun 是否被改回 False。
- **再驗**:把 WakeToRun 改回 False,夜檢必須判紅(已加該檢查)。
- **通則**:**「排程存在且 Ready」不等於「它會在該跑的時候跑」。** 排程的健康度有三層:存在 → 有下次執行時間 → **環境允許它在那個時間執行**。前兩層我早就在檢查,第三層今天才補。
- **殘留風險**:WakeToRun 只能叫醒**睡眠**中的機器,**完全關機救不了**。這一條要靠人:機器晚上別關,或改用一台常開的機器。

### A5|物件顏色寫死在程式的分類表裡,主題說白鞋也會畫出深藍鞋
- **症狀**:2026-08-14 slot1 主題「白鞋鞋邊泛灰」,生成出來是**深藍色帆布鞋**,而且鞋邊是乾淨的白 —— 主題講的缺陷根本不在畫面上,背景還有洗衣機(風格正本明文禁止)。
- **真因**:`contentPlan.ts` 的輪播提示詞把物件寫成**每個分類一個常數**:`headline === "鞋子"` → `"navy-and-warm-white sneakers"`。**深藍是寫死在程式裡的**,主題再怎麼說白鞋都沒用。而提示詞其餘部分只有「保持特徵物件一致」,從頭到尾沒說出物件是什麼。
