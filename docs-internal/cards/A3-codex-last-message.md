**1．什麼變化觸發入庫、完工通知**

Monitor 預設每輪先等 6 秒，再檢查 MDB 檔案修改時間；只有修改時間不同才查資料。6 秒是輪詢等待時間，還要加上查詢與推播耗時，不能視為送達時限。（M：86、144–157、241）

| 通知 | 實際觸發條件 | eHank 表／欄位與證據 |
|---|---|---|
| 收件入庫 | 查到 `Did > last_did` 的資料列，依 `Did` 升序逐件處理；找到綁定的 LINE 使用者就推播。 | `Det` 表；查詢 `Did, Dno, Cid, State, Dname, Price, Indate, Pdate`。（M：159–196） |
| 完工／可取 | `Datei` 非 NULL、非空字串，且 `Dater` 為 NULL 或空字串；另外要求 `Dno` 非空、尚未列入 `completed_dnos`。 | `Det` 表；查詢 `Did, Dno, Cid, State, Dname, Price, Datei, Loc`。（M：198–235） |

幾個關鍵差異：

- **入庫通知只看 `Did` 超過門檻。** 沒有再檢查是否今天收件、是否已取件，或是否只是匯入／補登的歷史資料。修改舊資料列但 `Did` 沒增加，也不會再觸發入庫通知。（M：160–162）
- **完工通知只依 `Datei`、`Dater` 與件號去重。** `Loc` 只讀取並寫入日誌，沒有要求已上架；也沒有以 `State == "完工"` 作為替代條件。（M：199–224）
- 兩種通知都是逐件發送；同一輪若新件也符合完工條件，可能先收到入庫、再收到完工訊息。（M：170–235）

`lookup_service.py` 本身不直接查 MDB，而是讀取 connector 的標準化快照。C：240–244 查 `Cus`、`Det`，C：310–318 的狀態規則為：

1. `Dater` 有值 → `picked`，已取件。
2. 否則 `Datei` 有值，**或 `State == "完工"`** → `ready`。
3. 其餘 → `processing`。

因此，**只有 `State="完工"`、但 `Datei` 空白的件，查件可顯示可取，monitor 卻不會發完工通知。** L：199–223 會排除已取件，並依上述標準化狀態組成查件結果。

D：36–43 只接受 `SELECT` 並以 `Mode=Read` 開啟資料庫；這證明 MDB 查詢的唯讀方式，與 LINE 推播是否安全、是否成功是兩個不同問題。

**2．去重、持久化，以及每天重開的影響**

`last_did` 是全域入庫進度門檻。每讀到較大的 `Did` 就先更新，之後才找客人並推播；沒有綁定或推播失敗，也會越過這筆。（M：170–196）

`completed_dnos` 是完工件號集合。程式發現新的可取件號後，**先加入集合，再查綁定與推播**；沒有綁定或推播失敗，仍會留在集合。（M：209–235）

每輪最後把兩者寫回 `data/monitor_state.json`；啟動時會重新載入。（M：102–113、237–240）

| 情況 | 實際結果 |
|---|---|
| 正常關機、狀態檔有效且前一輪已成功保存 | 重開後沿用門檻與集合，不會僅因重開而重發昨天已記錄的事件。啟動後仍會重新掃描，但會被去重條件擋住。（M：104–144、160–162、209–212） |
| 第一次啟動、沒有 state，且兩項基線查詢都成功 | 把目前 `MAX(Did)` 設為入庫基線，把目前已完工未取的件號全部加入集合；通常不會把歷史全部發出去。（M：117–142） |
| 入庫基線查詢失敗 | 程式把 `last_did` 設成 `"000000"` 後繼續執行；後續查詢恢復時，歷史上高於這個門檻的資料可能全部被當成新入庫，對符合綁定者推播。（M：118–125、160–196） |
| 完工基線查詢失敗 | 集合可能保持空白；後續查詢恢復時，既有已完工未取件可能全部被當成新完工。（M：127–134、199–235） |
| 推播成功後、保存 state 前中斷 | 重開仍讀到舊狀態，同一事件可能再發一次；目前沒有足以封住這個中斷空窗的持久化事件／收件人紀錄。（M：196、235、237–240） |

另有兩個漏發點：

- 狀態檔毀損或無法解析時會被當成 `{}`，重新建立基線，可能把尚未通知的事件直接納入基線略過。（M：106–134）
- `completed_dnos` 只要是空集合就會重新抓基線，即使 `last_did` 已存在；這種情況下，關機期間才完工的件也可能被直接列入已處理集合。（M：127–132）

程式沒有移除已取件件號的邏輯。因此 `completed_dnos` **不是成功送達清單，也不是目前店內可取件數**。

**3．錯發、漏發風險**

**收件人選錯的主要風險：**

- **查詢會直接建立／覆寫綁定。** 客人輸入能查到資料的手機或客號後，W：625–654 就呼叫 `save_binding()`；這條流程沒有驗證查詢者確實擁有該手機／客號。若查了別人的資料，後續可能收到別人的通知。W：127–142 會以同一 LINE 使用者為鍵覆寫其客號。
- **同客號多個 LINE 使用者會全部收到。** M：75–83 收集所有符合客號的綁定，M：188、227 逐一推播，沒有指定主要收件人或個別同意欄位。此次綁定複本有 **2 個 LINE 使用者、2 個不同客號**；去除客號前導零後仍為 2 組，未見同客號多人，但無法據此驗證綁定者身分。證據：[customer_bindings.json](C:/Users/cyc39/AI-Lanes/shop-pc-ops/20261029/customer_bindings.json:3)，客號欄位位於第 3、9 行；不列出個資。
- **通知與查件的客號判定不一致。** Monitor 只要 `Cid` 非空且不以 `@` 開頭就採用，否則採 `State`；connector 則先檢查 `Cid` 是否存在於 `Cus` 客號集合，再考慮 `State`。遇到歷史欄位異常時，兩條路線可能認定不同客人。（M：183、223；C：256–261、291–299）
- **件號重用主要造成漏發。** 完工去重只用 `Dno`，集合又不清除；新客件重用舊件號，會被略過。若兩筆資料共用同一 `Dno`，先處理的資料列會壓掉後面的通知。收件人仍來自各列客號，件號重用本身不會直接把收件人換成舊客人。（M：209–226）

**漏發／重發的主要風險：**

- **MDB 鎖住或查詢失敗，不保證下一個 6 秒重試。** 兩段查詢失敗都被轉為空結果，流程仍保存 state 並更新 `last_mtime`；若 MDB 修改時間之後沒有再變，就會一直略過查詢，直到再次變更或程序重開。（M：164–168、203–207、237–241）
- **Push 失敗沒有重試。** `push_message()` 遇到缺少 token 等條件直接回傳 `False`，連線失敗也回傳 `False`；兩處呼叫者都未檢查回傳值。去重狀態已先更新，因此之後通常不會再補發。（M：36–62、180–196、215–240）
- **綁定檔讀失敗會靜默視為無人綁定。** 事件仍被越過；之後修好綁定或新增綁定，也沒有補通知機制。（M：65–72、157–196、215–240）
- **狀態檔直接覆寫，沒有原子替換。** 寫入中斷可能造成檔案毀損；推播後未保存則可能重發。（M：142、240）
- **`Did` 重編或不再單調遞增可能漏發。** Python 端用字串比較大小，程式依賴其編碼與排序規則，沒有處理編號重置。（M：160–181）

還有資料來源風險：monitor 用固定路徑或備份路徑判斷修改時間；D：25–30 的實際查詢路徑另允許 `EHANK_MDB_PATH` 覆寫，也會自動退回備份。兩者沒有核對一致性，可能監看一份資料、查另一份資料，或把備份資料用於正式通知。（M：96–98、115；D：25–30）

以上是程式可形成的風險路徑；**本次未證明已發生實際錯發，也未驗證任何客人的手機送達情況。**
